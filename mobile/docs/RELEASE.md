# NearBitez Android — Release Guide

Everything needed to take the React Native app from this repository to the Play
Store, and the checks to run before each submission.

---

## 1. What decides which backend a build talks to

One place: `app.config.js`. `APP_ENV` selects a profile and `eas.json` sets
`APP_ENV` per build profile.

| APP_ENV | App name | Backend |
|---|---|---|
| `development` (default) | NearBitez Dev | `http://10.0.2.2:5000` (Android emulator → host) |
| `staging` | NearBitez Staging | `https://near-bitez.onrender.com` |
| `production` | NearBitez | `https://near-bitez.onrender.com` |

`src/constants/config.ts` throws at startup if a production build resolves to a
local or plain-HTTP address, so a misconfigured release fails loudly on the
first launch instead of silently reaching nothing.

A developer can override locally with a gitignored `.env`
(`EXPO_PUBLIC_API_URL`, `EXPO_PUBLIC_SOCKET_URL`). **Release builds ignore it.**

Nothing prefixed `EXPO_PUBLIC_` may ever hold a secret — it is compiled into the
bundle and readable from a downloaded APK.

## 2. One-time setup

```bash
npm install -g eas-cli
eas login                 # Expo account
cd mobile
eas build:configure       # links the project, writes the EAS project id
```

### Signing

Let EAS generate and hold the upload keystore:

```bash
eas credentials           # Android → Keystore → set up a new keystore
```

EAS stores it server-side, so it is never in the repository. `.gitignore`
already blocks `*.keystore`, `*.jks`, `*.p12`, `*.p8`, `credentials.json` and
`google-play-service-account.json`.

**Back the keystore up** (`eas credentials` → download) and keep it somewhere
durable. Losing it means never being able to update the published app — a new
key is a new listing, and existing installs cannot upgrade to it.

Prefer enrolling in **Play App Signing** so Google holds the app signing key and
the upload key can be rotated if it is ever lost.

## 3. Builds

```bash
# Internal test APK, staging backend — installable directly on a device
eas build --platform android --profile preview

# Play Store bundle, production backend
eas build --platform android --profile production
```

`production` emits an **.aab**, which is what the Play Console accepts.
`preview` emits an **.apk** for sideloading during testing.

`autoIncrement` on the production profile bumps `versionCode` per build. Bump
`VERSION` in `app.config.js` by hand when the user-visible version should change.

Submit:

```bash
eas submit --platform android --profile production
```

Uploads to the **internal** track as a **draft** — nothing reaches users until
promoted in the Play Console.

### Verifying a build without the store

```bash
npx --no-install tsc --noEmit                    # types
APP_ENV=production npx expo export --platform android   # production bundle compiles
```

## 4. Play Store listing

**App name:** NearBitez
**Short description (≤80):**
> Order food from restaurants near you, track it live, and play while you wait.

**Full description:**
> NearBitez connects you to restaurants around you — browse menus, order in a few
> taps, and follow your food from the kitchen to your door.
>
> • Discover nearby restaurants by cuisine, rating and delivery time
> • Live order tracking from accepted to delivered
> • Tiffin subscriptions for regular home-style meals
> • Play games while your order is being prepared and earn NearCoins
> • Daily leaderboard, streaks and reward coupons
> • Light and dark themes
>
> Restaurant owners get a full dashboard in the same app: live orders, menu and
> stock control, tiffin plans, delivery settings, subscription and commission
> reporting, payouts and customer messages.

**Category:** Food & Drink
**Content rating:** Everyone. The games contain no violence, gambling or
purchasable loot — rewards are earned by play and cannot be bought.

**Data safety — declare accurately:**

| Data | Collected | Why | Notes |
|---|---|---|---|
| Name, email, phone | Yes | Account, order contact | Linked to the user |
| Delivery address | Yes | Fulfilling orders | Linked to the user |
| Photos | Yes (vendors only) | Menu and store images | Uploaded to Cloudinary |
| Order history | Yes | Order tracking, support | Linked to the user |

- Data is encrypted in transit (HTTPS).
- No advertising identifiers, no third-party ad SDKs, no analytics SDK.
- Account deletion: currently only via support — **see Known Issues.**

**Also required:** a hosted privacy policy URL and a support email. Neither
exists in this repository; both must be supplied before submission.

## 6. Pre-submission checklist

Run through this on a **real device**, on the `preview` build, before promoting
anything.

### Configuration
- [ ] `APP_ENV=production` resolves to `https://near-bitez.onrender.com`
- [ ] `versionCode` is higher than the last uploaded build
- [ ] No `.env` committed; no keystore in git

### Authentication
- [ ] Customer sign-up, login, logout
- [ ] Vendor login lands on the vendor dashboard
- [ ] Admin login lands on the admin dashboard
- [ ] Session survives an app restart
- [ ] Expired/invalid token returns the user to login rather than a blank screen

### Customer
- [ ] Browse → search → restaurant → menu → cart → checkout → order placed
- [ ] Live tracking updates as the vendor advances the order
- [ ] Order history, profile edit, notifications

### Vendor
- [ ] New order arrives live; accept → preparing → ready → delivered
- [ ] Menu create/edit, availability toggle, image upload
- [ ] Inventory, tiffin, subscription, finance, messages

### Admin
- [ ] Dashboard, restaurants, orders, users, subscriptions, finance, analytics

### Games and rewards
- [ ] Each game: start, pause, resume, game over, restart
- [ ] Score submits and the reward shown matches the server response
- [ ] Leaderboard updates live
- [ ] Wait & Play appears while an order is being prepared and not after

### Resilience
- [ ] Airplane mode: clear message, retry works, nothing looks frozen
- [ ] Cold backend (first request after idle) succeeds — see §7
- [ ] Backgrounding mid-game pauses rather than losing the run

### Presentation
- [ ] Light and dark, every tab
- [ ] Small phone and large phone; no clipping or keyboard overlap

## 7. Backend notes that affect the app

**Cold starts.** The production backend sleeps when idle; a measured cold boot
took **33 seconds**. The API client keeps a 20 s timeout on the first attempt
and retries **GET** requests once with a 60 s timeout, which covers it. Writes
are never retried — a timeout does not prove the server did not process the
request, and a retried checkout would place a second order.

**Keeping it warm** (optional): a scheduled ping to
`/api/v1/settings/public` every 10 minutes removes the cold start entirely.

## 8. Release steps

1. Update `VERSION` in `app.config.js` if the user-visible version changes.
2. `npx --no-install tsc --noEmit` — must be clean.
3. `eas build --platform android --profile preview` → test on a device against §6.
4. `eas build --platform android --profile production`.
5. `eas submit --platform android --profile production` (internal track, draft).
6. Test the internal release: fresh install **and** upgrade over the previous build.
7. Promote internal → closed → production in the Play Console.
